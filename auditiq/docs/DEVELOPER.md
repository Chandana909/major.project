# Developer guide

For whoever changes the code. Read the [README](../README.md) first (what the
project is and how to run it), then [ARCHITECTURE.md](ARCHITECTURE.md) (the
design and why). This guide is the map of the code, the paths a request and an
invoice take through it, the contracts between its parts, how to extend it, and
the checks every change must pass.

## 1. Layout

```
auditiq/                  the Python project (run every command from here)
  auditiq/                the application package (pipeline, store, API, command line)
  auditiq_bench/          the generator of the synthetic ledgers (AuditIQ-Bench)
  evaluation/             the experiments; each writes its results under results/
  app/dashboard.py        the Streamlit dashboard
  frontend/               the web application (React, TypeScript, React Three Fiber)
  policy/                 the clause registries (JSON), the SOP texts, the policy PDFs and their variants
  data/                   the generated ledgers (regenerated byte for byte; hashes in each manifest)
  results/                every measured result, as the scripts wrote it
  tests/                  the Python tests (SQLite and PostgreSQL)
  scripts/                local PostgreSQL, the browser-test server, the one-command reproduction
  deploy/                 the Ollama Modelfile and the PostgreSQL compose file
  docs/                   this documentation
../RESULTS.md             every result for the paper, with its source and command
../REPORT.md              the full report, generated from the result files
../.github/workflows/ci.yml   continuous integration
```

## 2. The code, module by module

**The pipeline.** One invoice in, one audit pack out.

| Module | Responsibility | Start reading at |
|---|---|---|
| `extraction.py` | Joins the records linked to each invoice (PO, goods receipt, vendor, approvals, the vendor's other invoices) into one transaction, from CSV files | `extract()` |
| `history.py` | The vendor's other invoices as a list that carries an index of the vendor's invoices by number and by date, shared by the vendor's transactions | `History`, `VendorIndex` |
| `controls.py` | The twelve deterministic controls; each reads its thresholds from the clause registry and returns flags with evidence | `CONTROLS`, `run_controls()` |
| `prompts.py` | The prompt texts of the model stages, and their hash (frozen once a benchmark run starts) | `prompt_hash()` |
| `agents.py` | The three specialist agents, the single-prompt auditor (C2) and the challenger; JSON replies parsed and checked | `run_specialist()`, `run_challenger()` |
| `graph.py` | The LangGraph state graph; configurations C1 to C5 are subsets of its stages | `PRESETS`, `build_graph()` |
| `scoring.py` | Confidence from re-runs, the risk scores R0 and Rc, and the route (approve, sample, escalate) | `route()` |
| `audit_pack.py` | The record of one audited transaction, as stored and as shown | `render_markdown()` |
| `corrections.py` | The revision each control finding requires (amend, re-approve, reject, hold, obtain, verify), computed from its evidence and the policy | `correct()`, `apply()` |
| `service.py` | Batch audit over the store: extract, run the graph, store every result, set the workflow status | `audit_invoices()` |

**The policy.** A document in, an executable policy out.

| Module | Responsibility |
|---|---|
| `policy.py` | The policy store's object: one clause registry and one policy text per version |
| `policy_pdf.py` | Renders the sample policy documents as PDFs from the registries |
| `policy_ingest.py` | Reads a PDF into pages and passages, with clause numbers and page numbers, for search and citations |
| `policy_extract.py` | Reads the thresholds of a document in the template's wording (patterns, no model); refuses a document it cannot execute |
| `policy_llm.py` | Reads a document in its own wording: the model proposes values with quotes, the code verifies each quote, a person confirms |
| `simulation.py` | What a policy document would do to the stored ledger before it is adopted: a dry run of the controls under both policies |
| `retrieval.py` | Policy search: lexical ranking, question rewriting by the model, embeddings, and the hybrid of the two |

**The store and the data.**

| Module | Responsibility |
|---|---|
| `db.py` | The database on SQLite or PostgreSQL: one schema, the ledger, the policy store, results, flags, trail, review decisions, the views; extraction from the store (`extract_one`, `extract_many`) |
| `datadict.py` | The meaning of every table and column; writes `docs/DATA_DICTIONARY.md` |
| `ledger_import.py` | Reads a ledger from a folder, a zip archive of CSV files or an Excel workbook, and checks it before it replaces the stored one |

**The interfaces.**

| Module | Responsibility |
|---|---|
| `cli.py` | The `auditiq` command: `setup`, `ledger`, `policy`, `run`, `audit`, `show`, `queue`, `decide`, `ask`, `ask-data`, `serve`, `export`, `status`, `user`, `graph`, `check-llm` |
| `api.py` | The REST API (FastAPI): who is asking and what each role may do (`principal`, `require`), its background jobs and the rules that keep them apart, the security headers; serves the built web application |
| `apidoc.py` | Writes `docs/API.md` from the application |
| `copilot.py` | Questions about the policy (answered from passages, with citations) and about the data (one checked, read-only SELECT) |
| `app/dashboard.py` | The Streamlit dashboard |
| `frontend/src/` | The web application: `api/` (client and types), `pages/` (seven pages), `three/` (the 3D views), `components/` |

**Models and settings.** `llm.py` is the only code that talks to a chat
model: one OpenAI-compatible endpoint, retries with backoff, a context-size
guard, and a response cache keyed by the whole request. `config.py` reads the
settings from the environment and `.env` (OPERATIONS.md, Section 3, lists
every variable).

**The benchmark and the evaluation.** `auditiq_bench/` generates the ledgers
and their ground truth (`generator.py`, `export.py`, `validate.py`,
`taxonomy.py`); `evaluation/` holds one script per experiment, each writing
`results/<name>.json` and `.md`, and the scripts that collect them
(`collect_results.py` into `results/results.json`, `full_report.py` into
`../REPORT.md`, `figures.py`).

## 3. Three paths through the code

**An invoice, from the ledger to the review queue** (`auditiq run --config C1`).

1. `cli.cmd_run` opens the store and calls `service.audit_invoices` with the
   configuration, the active policy and the invoice ids.
2. `db.extract_many` reads the five ledger tables once and builds one
   transaction per invoice; each vendor's invoices are indexed once
   (`history.VendorIndex`) and shared by its transactions.
3. `graph.invoke` runs the stages of the configuration: extraction is done,
   so `controls.run_controls` runs the twelve controls against the registry;
   with C3 to C5 the agents, the challenger and confidence follow.
4. `scoring` turns the flags into R0, Rc and a route; `audit_pack` assembles
   the record.
5. `db.save_result` stores the result, its flags with evidence and the trail;
   `service.workflow_status` makes it `AUTO_APPROVED`, `PENDING_REVIEW` or
   `NOT_SAMPLED`. Results are committed in batches of 200.
6. The view `v_review_queue` lists what waits for a person; a decision
   (`POST /api/results/{id}/decision`, or `auditiq decide`) is stored next to
   the result, never in place of it.

**A policy document, from upload to execution.**

1. `POST /api/policy/preview` stores the PDF under an id and calls
   `policy_extract.build`, which reads every rule's thresholds and compares
   them with the active version. Nothing is stored in the database.
2. `POST /api/policy/adopt` stores the new registry and ingests the
   document's passages (`policy_ingest.ingest`); a document that cannot be
   executed is refused with its problems (422).
3. `POST /api/policy/activate` makes it the active version;
   `POST /api/policy/apply` audits the whole ledger again under it, as a job.
   No code changes: the controls read the registry at run time.

**A request from the web application.** `frontend/src/api/client.ts` adds
the token from `sessionStorage` and calls the endpoint; FastAPI checks the
token (`authorised`, constant-time) and opens a connection for the request
(`connection`, closed afterwards); the answer is JSON, and an error's
`detail` is shown on the page. A long task answers 202 with a job, which the
page polls at `GET /api/jobs/{id}`.

## 4. Contracts between the parts

**A transaction** (built by `extraction.extract` and `db.extract_many`):

```
{"invoice": {...}, "po": {...} | None, "grn": {...} | None, "vendor": {...},
 "approvals": [{...}, ...], "vendor_history": History([{...}, ...])}
```

The fields of each record are the `*_FIELDS` lists of `extraction.py`. The
stages only read a transaction. `vendor_history` behaves as a list everywhere
(JSON writes it as one, slicing gives a plain list); the two controls that
compare an invoice with the vendor's others use its index when it has one and
read the list when it does not, with the same findings
(`tests/test_controls.py`).

**A flag** (from a control or an agent):

```
{"clause": "4.1.1", "control": "same_day_splitting", "severity": "high",
 "source": "D" | "L", "confidence": 1.0, "evidence": [{"field": ..., "value": ...}], "message": "..."}
```

Every flag names its clause and carries the evidence it was raised on; an
agent's flag (`source` L) is checked against the agent's remit and the
evidence it was shown.

**The clause registry** (`policy/policy_v<version>.json`, and every adopted
document in `company_policies`): `{"policy_name", "version",
"effective_date", "clauses": {"4.1.1": {"title", "severity", "kind",
"params": {...}}}}`. Every threshold the system applies is a `params` value.
**No threshold is written in code**; a change of policy is a new registry,
never an edit.

## 5. Extending it

**A new control.** (1) Add the clause and its parameters to the registries
under `policy/` and render the texts (`python policy/build_policy.py`). (2)
Write the control in `controls.py` as a function of the transaction and the
clauses, reading every threshold from `clauses[...]["params"]`, returning
`make_flag(...)` with evidence; add it to `CONTROLS`. (3) Teach the reader the
wording of its parameters (`PATTERNS` in `policy_extract.py`), so that a
document can change them. (4) Test it in `tests/test_controls.py`: the clean
transaction raises nothing, the violating one raises exactly this flag, and the
threshold is read from the registry. (5) If the benchmark should contain the
anomaly, add the class to `auditiq_bench/taxonomy.py`, its injection to the
generator and its check to `validate.py`, then regenerate the datasets and the
results that depend on them.

**A change of threshold** is never a code change: write the document, adopt
it, activate it (Section 3). That is the feature the project measures.

**A new endpoint.** Add the route to `create_app` in `api.py` with a tag,
`dependencies=protected` unless it must be open, a docstring (it becomes the
description in `/api/docs` and `docs/API.md`), a pydantic model for its body
with limits on every string, and `Depends(connection)` if it reads the store.
Long work goes in a job (`request.app.state.jobs.start(kind, work)`); if the
job changes the ledger or audits it, add its kind to `CONFLICTS`. Then
`python -m auditiq.apidoc`, a function and types in `frontend/src/api/`, and a
test in `tests/test_api.py` (the `client` fixture runs it on both backends).

**A page of the web application.** A component in `frontend/src/pages/`, a
route in `App.tsx`, a test in `pages.test.tsx` against the mocked client, and,
for a path a user takes, a browser test in `frontend/e2e/app.spec.ts` against
the real server.

**A table or a column.** Change `SCHEMA` in `db.py` (one schema for both
backends; the schema id changes with it, so an old store is rebuilt), describe
it in `datadict.py` (`TABLES`), and `python -m auditiq.datadict`. A test fails
until every column is described.

**An experiment.** A script `evaluation/<name>.py` that writes
`results/<name>.json` and `.md` from committed inputs only; an entry in
`collect_results.py` (and a section in `full_report.py`); a step in
`scripts/reproduce.py` if it needs no model; the result in `../RESULTS.md`
with its label (measured, pilot or sample) and its command.

## 6. Conventions

- **Every number comes from a script.** A result is written by a script of
  `evaluation/` into `results/`; documents quote those files. Nothing
  unmeasured is presented as measured (RESULTS.md, the labels).
- **Generated files are never edited by hand**: `docs/DATA_DICTIONARY.md`,
  `docs/API.md`, `docs/DATASETS.md`, `../REPORT.md`, `results/results.json`
  and the datasets. Each has a generator and a test that it is current.
- **Both backends.** A test that touches the store takes the `backend`,
  `library` or `ledger` fixture and runs on SQLite and on PostgreSQL; without
  a reachable test database (`AUDITIQ_TEST_DATABASE_URL`) the PostgreSQL runs
  are skipped, and CI always has one.
- **Every connection is closed.** A command's connections are closed when it
  ends (`cli._opened`), a request's by its dependency, a job's by its
  `finally`. An unclosed connection on PostgreSQL keeps its transaction and its
  locks (CODE_REVIEW.md, finding 2).
- **Models only through `llm.ChatClient`**, so that every call is cached,
  retried, size-checked and counted. Prompts are frozen during a benchmark
  run: `evaluation/run_full.py` refuses to start if their hash changed.
- **Files the scripts write use LF line endings** and stable ordering, so that
  a regenerated file compares equal to the committed one.
- **Secrets only in `.env`** (ignored by git) or the environment; a URL with a
  password is never printed (`auditiq status` shows the host only).
- **Style.** `ruff` with the rules in `pyproject.toml`; type hints on public
  functions; a docstring on every module and endpoint; comments say why, not
  what.

|---|---|---|
| Lint | `ruff check .` | test job |
| Python tests, SQLite and PostgreSQL | `python -m pytest` | test job; again against the compose database |
| Frontend lint, types, tests, build | `cd frontend && npm run lint && npm run typecheck && npm test && npm run build` | frontend job |
| Frontend dependencies | `npm audit --omit=dev` | frontend job |
| Browser tests against the real server | `cd frontend && npm run e2e` | e2e job |
| Python dependencies | `pip-audit --skip-editable` | test job |
| PostgreSQL from the compose file | `docker compose -f deploy/postgres/docker-compose.yml up -d --wait`, then the tests and a ledger set up and audited | compose job |

| Every result without a model | `python scripts/reproduce.py` (about an hour) | not in CI |

## 8. Logs and debugging

The command line, the server and the dashboard log in one format
(`config.configure_logging`); `AUDITIQ_LOG_LEVEL=DEBUG` shows every
connection, every model call's size and time, and every retry. A failed job
keeps its error (`GET /api/jobs/{id}`) and the server logs its traceback. Every
model reply is in the response cache (`.auditiq/llm_cache.sqlite`), so a run
can be replayed without the model. OPERATIONS.md, Section 11, lists the usual
problems and their remedies.
