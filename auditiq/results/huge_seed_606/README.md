# Dataset `huge_seed_606`

The huge ledger: 500,000 invoices from 15,000 vendors at the anomaly rate of the large ledger (714 invoices of each of the fourteen classes, 2.0%), with 720 hard negatives. It measures the controls, the classical detectors, the policy change and the application at a scale 25 times the large ledger and 100 times a benchmark ledger.

Generated by `python -m auditiq_bench --only huge_seed_606` (generator 1.0, seed 606, policy v2.5). The same command gives byte-identical files; `manifest.json` holds their SHA-256 hashes. Everything is synthetic: no vendor, person or invoice is real.

## Files

| File | Rows | Content |
|---|---|---|
| `vendor_master.csv` | 15,000 | one row per vendor: name, GSTIN, category, blacklist flag, registration status |
| `purchase_orders.csv` | 498,096 | what was ordered: amount, quantity, unit price, description |
| `goods_receipts.csv` | 497,858 | what was received against a PO: quantities and the receiver's remarks |
| `invoices.csv` | 500,000 | what the vendor billed, with its PO and GRN references |
| `approval_logs.csv` | 567,123 | who forwarded or approved each invoice, with role and time |
| `labels.csv` | 500,000 | ground truth of every invoice; never read by the pipeline |
| `eval_subset.csv` | 12,744 | the invoices the LLM configurations audit, with weights |
| `manifest.json` | | seed, versions, counts, file hashes |

The five record tables hold 2,078,077 records. Their columns are described in `docs/DATA_DICTIONARY.md`; they load into the database with `python -m auditiq setup --dataset <folder>`.
Invoices are dated 2025-04-01 to 2026-03-31.

## Ground truth

9,996 of the 500,000 invoices are anomalous (2.0%), 720 are hard negatives and 489,284 are ordinary clean invoices.

| Class | Anomaly | Rule(s) | Decided by | Severity | Invoices |
|---|---|---|---|---|---|
| R1 | Invoice amount differs from PO amount beyond the tolerance | 2.1.1 | a control | high | 714 |
| R2 | Billed quantity exceeds received quantity | 2.1.2 | a control | high | 714 |
| R3 | Duplicate invoice number for the same vendor | 2.2.1 | a control | critical | 714 |
| R4 | Malformed GSTIN or invalid state code | 3.1.1, 3.1.2 | a control | medium | 714 |
| R5 | Invoice GSTIN differs from the vendor master | 3.1.3 | a control | high | 714 |
| R6 | Same-day invoice splitting above the daily count | 4.1.1 | a control | high | 714 |
| R7 | Invoice amount exceeds the approver's limit | 5.1.1 | a control | critical | 714 |
| R8 | Missing PO or GRN reference | 2.1.3 | a control | high | 714 |
| R9 | Vendor blacklisted or suspended | 4.4.1 | a control | critical | 714 |
| R10 | Weekend-dated or round-amount invoice | 4.2.1, 4.3.1 | a control | low or medium | 714 |
| J1 | Near-duplicate invoice: re-keyed number, same vendor and amount | 2.2.2 | an agent | critical | 714 |
| J2 | Cross-day structuring just below an approval limit | 4.1.2 | an agent | high | 714 |
| J3 | Invoice description inconsistent with the PO description | 2.1.5 | an agent | medium | 714 |
| J4 | GRN remark contradicts the billed quantity | 2.1.4 | an agent | high | 714 |

Hard negatives are clean invoices built to resemble an anomaly:

| Type | Description | Invoices |
|---|---|---|
| HN_TOLERANCE | Invoice-PO variance just inside the tolerance (resembles R1) | 144 |
| HN_DAILY_LIMIT | Invoice count exactly at the daily limit (resembles R6) | 144 |
| HN_NEAR_LIMIT | Amount just inside an approval limit (resembles R7 and J2) | 144 |
| HN_SIMILAR_NUMBER | Consecutive invoice numbers and equal amounts for separate deliveries (resembles J1) | 144 |
| HN_RECURRING | Identical recurring monthly amounts (resembles R3 and J1) | 144 |

`labels.csv` columns: `invoice_id`; `label` (clean, hard_negative, anomalous); `class_id`; `clause_ids` (the violated rules, separated by `|`); `severity`; `group_id` (invoices that form one case, such as a same-day group); `related_invoice_id` (the original that a duplicate copies); `hard_negative_type`; `note` (what was injected, in words).

## Evaluation subset

| Stratum | Invoices | Weight |
|---|---|---|
| anomalous | 9,996 | 1.000 |
| ordinary | 600 | 813.093 |
| hard_negative | 720 | 1.000 |
| duplicate_original | 1,428 | 1.000 |

The weights sum to 500,000, the number of invoices. The controls and the classical detectors are evaluated on the whole ledger; the LLM configurations audit this subset, with the whole ledger as the vendor history, and their rates are computed with the weights.
