# AuditIQ: methodology, results and analysis

The full report of the measured work: how every experiment was designed and run, every result in detail, and what the results show. It is generated by `python -m evaluation.full_report` from the result files, the datasets and the code's own constants: **no number in it is typed by hand**, and a test fails if it is out of date. For writing the paper, the shorter guide is [`RESULTS.md`](https://github.com/Chandana909/major.project/blob/main/RESULTS.md); for programs and other models, every result is in [`auditiq/results/results.json`](https://raw.githubusercontent.com/Chandana909/major.project/main/auditiq/results/results.json); the paper is [`paper/auditiq_paper.pdf`](https://github.com/Chandana909/major.project/blob/main/paper/auditiq_paper.pdf).

Kinds of number: **measured** (a script of the repository produced it on the data stated), **pilot** and **sample** (measured on 20 or 34 invoices; no difference between configurations can be claimed), and **expected** (a target fixed before measurement, never a result; only in RESULTS.md, Section 10).

## 2. The system under test

AuditIQ audits procure-to-pay transactions: each vendor invoice with the purchase order (PO), goods receipt (GRN), vendor master record, approval log and the vendor's other invoices that it links to. The pipeline is a LangGraph state graph (`auditiq/graph.py`): evidence extraction, then the deterministic controls, then the language-model stages, then scoring and routing, then human review and the audit pack. Every result, finding (with its evidence), challenger removal and audit-trail entry is stored in SQLite or PostgreSQL; results are added and never replaced. The configurations compared are subsets of the same stages:

| Configuration | What runs | Controls | Language model | Challenger | Confidence |
|---|---|---|---|---|---|
| C0-IF, C0-SVM | Isolation forest and one-class SVM on 21 generic tabular features (Section 7) | no | no | no | no |
| C1 | The twelve deterministic controls only | yes | no | no | no |
| C2 | One language-model prompt over the whole policy and the invoice's records; no controls | no | single prompt | no | no |
| C3 | Controls, then three specialist agents in parallel | yes | 3 specialists | no | no |
| C4 | C3, then a challenger that may only remove agent findings | yes | 3 specialists | yes | no |
| C5 | C4, then confidence from grounding, clause validity and agreement over 3 re-runs; low-confidence findings go to sampled review | yes | 3 specialists | yes | yes |

The specialists' remits follow the sections of the policy; a finding that cites a rule outside the agent's remit is discarded by code. Each agent sees only the records its rules need:

| Agent | Policy sections | Records shown | Fields of the vendor's other invoices |
|---|---|---|---|
| Math and Approvals agent | 2.1, 5 | po, grn, approvals | – |
| Tax and Identity agent | 2.2, 3 | vendor, history | invoice_id, invoice_number, date, amount, po_id, grn_id |
| Vendor Intelligence agent | 4 | vendor, approvals, history | invoice_id, date, amount, description, approver_role, approver_name |

Language-model settings (`auditiq/graph.py`): temperature 0.0 for every stage; the agreement re-runs of C5 use temperature 0.7. An agent sees at most 40 of the vendor's other invoices per selection rule (Section 20 checks that no labelled case loses an invoice it depends on). The prompts contain no threshold and no rule number: the policy text is inserted at run time, so the policy document is the only place a threshold is stated. A reply that is not valid JSON is sent back once for repair; a stage that still fails is recorded as failed and contributes no finding.

## 3. The policy as data

A policy version is a tuple P = (K, s, κ, θ): the set K of rule identifiers, the severity s(k) of each rule, its kind κ(k) (control: decidable by comparing fields; judgement: needs reading), and its parameters θ_k. Stored as data it is the clause registry. The reference policy, version 2.5, has 16 rules, 12 of kind control and 4 of kind judgement, with 14 parameter values:

| Rule | Title | Severity | Decided by | Parameters (version 2.5) |
|---|---|---|---|---|
| 2.1.1 | Amount match | high | control (code) | `amount_tolerance_pct` = 1.0 |
| 2.1.2 | Quantity match | high | control (code) | – |
| 2.1.3 | Missing reference | high | control (code) | – |
| 2.1.4 | Receipt remarks | high | agent (judgement) | – |
| 2.1.5 | Description match | medium | agent (judgement) | – |
| 2.2.1 | Exact duplicate | critical | control (code) | – |
| 2.2.2 | Near duplicate | critical | agent (judgement) | – |
| 3.1.1 | GSTIN format | medium | control (code) | `gstin_length` = 15 |
| 3.1.2 | GSTIN state code | medium | control (code) | `state_code_min` = 1; `state_code_max` = 37 |
| 3.1.3 | GSTIN vendor match | high | control (code) | – |
| 4.1.1 | Same-day splitting | high | control (code) | `max_invoices_per_vendor_per_day` = 3 |
| 4.1.2 | Structuring across days | high | agent (judgement) | `guide_window_days` = 7; `guide_band_pct` = 15 |
| 4.2.1 | Weekend date | medium | control (code) | `non_business_days` = ["Saturday", "Sunday"] |
| 4.3.1 | Round amount | low | control (code) | `round_amount_multiple` = 10000 |
| 4.4.1 | Blocked vendor | critical | control (code) | `blocked_gstin_statuses` = ["Suspended"] |
| 5.1.1 | Approval limit | critical | control (code) | `approval_limits` = {"Manager": 100000, "Senior Manager": 500000, "Director": 2500000, "CFO": 10000000} |

Version 2.6 differs from 2.5 in: `amount_tolerance_pct` of rule 2.1.1: 1.0 to 5.0; `max_invoices_per_vendor_per_day` of rule 4.1.1: 3 to 5; `approval_limits` of rule 5.1.1: {"Manager": 100000, "Senior Manager": 500000, "Director": 2500000, "CFO": 10000000} to {"Manager": 150000, "Senior Manager": 500000, "Director": 2500000, "CFO": 10000000}.

**From document to registry** (`auditiq/policy_extract.py`, no language model). The PDF is read line by line with font size, position and page (PyMuPDF). The most frequent font size is the body size; a line at least one point larger is a heading; a line that begins with "Rule <number> (<severity>)," opens a rule, and indented lines continue it. For each parameter one pattern is matched against the text of the rule that states it; the approval limits are read from the table of roles and amounts. The set of rules and their kinds come from a reference version, which records what the system is able to execute. A document is refused, and nothing is stored, when a rule the system executes is absent, a threshold is not found in the wording of its rule, the document contains a rule for which there is no control, a value is not meaningful, the document states no version, a rule is stated more than once, or the approval table lacks a role the system applies.

**Controls** (`auditiq/controls.py`). A control c_k(x; θ_k) is a pure function of one transaction x and the parameters of its rule. It returns nothing or a finding f = (k, s(k), E), where E is the set of field values it rests on. A control contains no constant of its own; amounts are compared in integer paise, so rounding cannot move a decision at a boundary. The controls are written from the policy text and import nothing from the dataset generator (a test enforces this).

## 4. Scores, confidence and routing

(`auditiq/scoring.py`.) With severity weights critical 30, high 20, medium 10, low 5, the count-based score of an invoice x with findings F(x) is

    R0(x) = min(100, Σ_{f ∈ F(x)} w_{s(f)}),

raised to at least 70 if F(x) contains a critical finding and to at least 50 if it contains a high one. The confidence of a finding is c(f) = 1 for a control and c(f) = (g + p + a) / 3 for a model finding, where g = 1 if every evidence field exists in the transaction with the stated value, p = 1 if the cited rule exists in the active policy, and a is the share of the re-runs of the originating agent that cite the same rule. The confidence-weighted score is

    Rc(x) = min(100, Σ_f w_{s(f)} · c(f)),

with the floors applied only for findings whose confidence is at least θ = 0.667. The route is: escalate to a reviewer if Rc ≥ τ = 50; sampled review if Rc < τ ≤ R0; approve otherwise. A finding that cites a valid rule takes that rule's severity, whatever the model stated. Risk levels: CRITICAL from 70, HIGH from 50, MEDIUM from 30, LOW below. Without C5's confidence term, Rc = R0 and no invoice is sampled.

## 6. Metrics

Definitions as implemented in `evaluation/metrics.py`. Every rate is a ratio of (weighted) sums over invoices, so the same code serves whole ledgers (weight 1) and the weighted evaluation subset.

| Metric | Definition | Note |
|---|---|---|
| Recall (invoice level) | Anomalous invoices reported at all / anomalous invoices | a detector names no rule, so this is the only level at which C0 and C1 can be compared |
| Precision (invoice level) | Anomalous invoices among those reported / invoices reported |  |
| F1 | 2·TP / (2·TP + FP + FN) |  |
| False-positive rate, ordinary / hard negatives | Ordinary (hard-negative) invoices reported / ordinary (hard-negative) invoices | hard negatives resemble an anomaly |
| Precision at 2% prevalence | 0.02·recall / (0.02·recall + 0.98·FPR) | precision if 2% of invoices were anomalous |
| Detected share of a class | Invoices of the class reported at all, whatever rule is cited |  |
| Per-class recall, precision, F1; macro-F1 and macro-recall | Computed on the classes of the cited rules; macro over rule-defined (R1-R10) and judgement (J1-J4) classes separately | only for configurations that cite rules |
| Citation correctness | Findings on anomalous invoices that cite a rule the invoice violates / findings on anomalous invoices |  |
| Model findings naming a violated rule | Findings raised by a language model that cite a rule the invoice violates / all findings a model raised (one on an invoice without an anomaly counts as wrong) | the share of the model's findings an auditor can rely on |
| Exact match | Invoices whose set of cited rules equals the true set |  |
| Escalation precision / recall | Escalated invoices with a high or critical true violation / escalated invoices; / invoices with a high or critical true violation |  |
| Policy adherence A(P) | Share of invoices whose set of cited rules equals the ground truth recomputed under policy P | Sections 11, 12 |
| Frozen-system errors | Unsupported findings (cited, not violated), missed exceptions (violated, not cited), needless and missed escalations under the count-based score with τ = 50 | Sections 11, 12 |
| Values read correctly; rules read word for word | Extracted parameter equal to the intended one; rule text equal to the rendered rule | Sections 11-13 |
| Recall@k, MRR | Answering passage among the top k; mean reciprocal rank of the answering passage | Section 19 |

## 7. Statistical procedure

**Confidence intervals.** 95% percentile bootstrap over invoices with 1,000 resamples (seed 0); on the evaluation subset the resampling is stratified by stratum (`evaluation/metrics.py`).

**Paired tests.** McNemar's exact test on paired per-invoice correctness of two systems scored on the same invoices, with Holm's step-down correction over the family of comparisons (`evaluation/stats.py`). For the detector comparison an invoice is correct when "reported or not" equals "anomalous or not"; for the language-model configurations, when the set of cited rules equals the true set.

**Thresholds of the classical detectors** (`evaluation/run_c0.py`). The isolation forest (300 trees) is fitted without labels on all invoices; the one-class SVM (RBF kernel, ν = 0.1) on clean invoices of the training folds. A detector outputs a score; the threshold is set by five-fold cross-fitting, folds stratified by class: each fold is decided with the threshold that maximises F1 on the other four, so no invoice is decided with a threshold tuned on its own label. The detectors therefore use labels the controls never see. Their 21 features are generic and encode no policy threshold: `log_amount`, `amount_to_po`, `quantity_minus_received`, `ordered_minus_received`, `missing_po`, `missing_grn`, `weekday`, `weekend`, `vendor_same_day`, `vendor_within_week`, `vendor_same_number`, `vendor_same_amount`, `vendor_same_po`, `amount_to_approver_limit`, `approval_entries`, `gstin_equals_master`, `gstin_length`, `vendor_blacklisted`, `vendor_registration_active`, `amount_trailing_zeros`, `log_amount_vs_vendor`.

**What is fixed by construction.** The controls and the ground truth (the generator's validator) are two implementations of the same written rules by the same authors. The controls' perfect scores on R1 to R10 and the policy-driven adherence of 1.000 therefore verify the implementation and the reading of each document; they are not detection results. The quantities not fixed by construction are the detectors' scores, the frozen system's errors, the reader's outcomes on held-out and edited documents, and everything a language model does.

## 9. Environment and reproducibility

All experiments ran on one laptop: Intel64 Family 6 Model 154 Stepping 4, GenuineIntel, Python 3.11.3, 12 logical CPUs (an Intel i5-1235U: 2 performance and 8 efficiency cores), 16 GB of memory, no GPU, Windows 11. Timings are those of this machine and depend on its load; counts, decisions and intervals do not.

Reproduction from a clone, in `auditiq/`: `pip install -e ".[dev]"`, then the commands of Section 8 (the order and the outputs are listed in [`RESULTS.md`](https://github.com/Chandana909/major.project/blob/main/RESULTS.md), Section 13). The datasets regenerate byte for byte; every experiment that needs no model was re-run with the final code and gave identical counts, values, decisions and intervals; the experiments with a model reproduce exactly from the cached replies. Continuous integration runs the Python tests on SQLite and PostgreSQL and the frontend checks on every push.

### 18.3 What the sample shows

- **Judgement anomalies.** The agents (C3) reached a macro-recall of 0.600 on the four judgement classes: J1 1.000, J2 0.400, J3 0.200, J4 0.800. The two classes found best are the ones whose evidence sits in one record the agent is shown (a repeated amount and PO; a remark in the goods receipt); the two found least need a comparison across several invoices or of two texts' meaning. That is a reading of five invoices per class, not a measured cause.
- **Reliability of a finding.** Only 0.375 of the agents' findings name a rule the invoice violates (0.471 after the challenger), and the agents flagged hard negatives at a rate of 0.800.
- **The challenger trades recall for precision.** It lowered the hard-negative false-positive rate from 0.800 to 0.400, but J1 recall fell from 1.000 to 0.200: it removed correct near-duplicate findings along with wrong ones.
- **Confidence measures stability, not correctness.** C5 sent 4 invoices to sampled review, 3 of them true anomalies. Of the model findings C5 kept, 6 of 9 wrong ones and 5 of 8 right ones had full agreement over the re-runs: agreement does not separate right findings from wrong ones.
- **Without the controls the model errs on almost every invoice.** The single prompt (C2) flagged every ordinary invoice (false-positive rate 1.000) and only 0.031 of its findings name a violated rule; its invoice-level recall of 0.900 comes from flagging nearly everything.
- **Cost.** Model calls per invoice: C2 1.210, C3 3.000, C4 3.740, C5 5.240; on the laptop's CPU a call took minutes, so a benchmark ledger needs a GPU or a hosted endpoint.
- **No difference between configurations is significant** on 34 invoices (table above); these are observations on a sample, not estimates for the benchmark.

## 22. What the errors show

- **Classical detectors find what is statistically unusual, not what is against the rules.** The isolation forest reports at least 90% of classes R3, R4, R5, J1 (Section 10.6); an anomaly of each of these classes sets a feature that is rare among clean invoices (R3: `vendor_same_number`; R4: `gstin_equals_master`; R5: `gstin_equals_master`; J1: `vendor_same_amount, vendor_same_po`), and rare values are what an isolation forest isolates first. The one-class SVM reports at most 10% of the rule-defined classes R4, R5, R8, R9, each marked by binary indicators (R4: `gstin_equals_master`; R5: `gstin_equals_master`; R8: `missing_po, missing_grn`; R9: `vendor_blacklisted, vendor_registration_active`). The indicator `gstin_equals_master` alone separates R4 and R5 from every ordinary invoice on `bench_seed_101` (the GSTIN differs from the registered one on 30 of 30 R4 and 30 of 30 R5 invoices, and on 0 of 4,460 ordinary ones), yet the SVM reports 0.033 and 0.033 of them; a plausible reading, not tested here, is that an RBF kernel on standardized features gives one rare indicator little weight against the continuous features. Neither detector finds J2, J3, J4 (at most 25%): J3 and J4 change no feature the detectors read (descriptions and receipt remarks are text); a J2 invoice differs from ordinary ones only by degree (an amount just below the approver's limit, several invoices of the vendor within a week), and the forest reports 0.222 of them, the SVM 0.067. Both report near-duplicates (J1), whose copied amount and PO are unusual, but neither names a rule, so an auditor still has to find out why an invoice was flagged.
- **A frozen system fails silently.** A tightened policy makes it miss exceptions and approve invoices the policy sends to review; nothing in its output shows the error. This is the operational argument for reading thresholds from the document instead of typing them into prompts and code.
- **The reader's failures were ambiguity, not misreading.** No harmless edit was misread; the two gaps found were documents that state a rule twice or omit a role, where any choice is a guess. Refusal with the reason is the safe answer.
- **A model's policy reading fails on use, not on transcription.** Its wrong values that passed the check are real words of the quoted passage put to the wrong use; a quote check cannot see that.
- **The language-model stages fail on reasoning across records and on precision.** In the per-invoice tables of Section 18, near-duplicates and goods-receipt remarks are found from the records shown; structuring across days and description mismatches are mostly missed; wrong near-duplicate findings appear on hard negatives built to resemble them; the challenger removes right and wrong findings alike.

## 23. Threats to validity

- **Internal (circularity).** The controls and the ground truth implement the same written rules by the same authors; perfect scores on R1-R10 and adherence of 1.000 verify the implementation and the reading of each document, not the rules' ability to catch fraud. The detectors use labels for their thresholds; the controls use none.
- **Construct (synthetic data).** The ledgers are generated; counts describe how these ledgers react, not the books of a particular organisation. Anomalies are injected one at a time into otherwise clean transactions.
- **External (one model, one machine).** The language-model results come from one 7B model on a laptop CPU and do not estimate what a larger model would do. Everything ran on one machine; the platform's services are separable, but a multi-machine deployment has not been measured.
- **Statistical (sample size).** The language-model stages were measured on 20 and 34 invoices; intervals are wide and no difference between configurations is significant. The free-form policy study has six documents written by the authors; the retrieval study sixteen questions per cell.
- **Researcher degrees of freedom.** Prompts were tried only on the development ledger and frozen (one prompt hash for every run); the free-form policy errors were deliberately not fixed, because that would be tuning on the evaluation set; the robustness gaps were fixed and both runs are reported.

## 24. What is not measured

- Configurations C2 to C5 on whole benchmark ledgers (about 1,200 invoices of the evaluation subset with three to five calls each); this needs a GPU or a hosted model endpoint. The paper states expected values for it, fixed before measurement (RESULTS.md, Section 10).
- A second model on the main comparison, the consistency subset, and the policy swap under the language-model configurations.
- A deployment on several machines.
